# Agent Evaluation Toolkit

Minimal research toolkit for evaluating enterprise AI agent workflows from logs.

This is the executable research artefact for Bruno Miguel Lopes da Rocha Fernandes's
dissertation, *Measuring Productivity Impact in Enterprise Agentic AI Architectures*.
The dissertation toolkit version is **0.4.0**. See [REPRODUCIBILITY.md](REPRODUCIBILITY.md)
for the locked environment, sample run, public verification commands, and the
distinction between the public source release and author-retained evaluation records.
Citation metadata is provided in [CITATION.cff](CITATION.cff); reuse is governed by
the [MIT licence](LICENSE).

The toolkit is intentionally narrow:

- unit of analysis: workflow run
- scope: one pilot workflow family
- priority: correctness, reproducibility, and auditability
- explicit handling of missing telemetry and assumption-based estimates

## What the toolkit does

- ingests raw logs
- normalizes them into a small internal telemetry model
- reconstructs workflow runs
- validates minimum telemetry requirements from an evaluation manifest
- computes first-pass workflow-run metrics
- applies measurement-window filtering
- prepares offline OTLP/JSON OpenTelemetry logs for the canonical pipeline
- profiles vendor-neutral source structure and assesses mapping readiness and friction
- assigns blocked, mapping-only, partial, or complete evidence tiers
- quarantines locally invalid runs after identity is trustworthy
- exports telemetry validation, exclusions, redaction reporting, an evaluation package, a JSON scorecard, and a Markdown evaluation report

## Current scope

This is a pilot-ready framework, not a fully generic platform.

- It is packaged as a Python project and can be installed into a virtual environment.
- It currently supports one workflow family at a time through a workflow config file.
- It preserves traceability from outputs back to raw telemetry through evidence references.
- It preserves traceability to evaluation design and configuration evidence through an evaluation manifest.
- It avoids carrying unrestricted raw payload fields into derived outputs; copied evidence fields are allowlisted and can be redacted.
- It reports missing telemetry explicitly instead of inventing values.
- It keeps observed metrics separate from assumption-based estimates.
- It writes input and artefact fingerprints so future enterprise runs can be audited without retaining raw payloads.

## Assess enterprise mapping readiness

Profile source fields and types without retaining their values, then record the canonical mapping and optional activity log:

```bash
agent-eval-toolkit assess-mapping \
  --source-profile data/mapping_samples/source_profile.complete.json \
  --mapping-spec data/mapping_samples/mapping_spec.confirmed.json \
  --evaluation-manifest data/mapping_samples/manifest.mapping.json \
  --activity-log data/mapping_samples/mapping_activity.complete.jsonl \
  --output-dir mapping-assessment
```

The friction output is deliberately multidimensional. Recorded effort remains null when no activity log exists; a partial log yields only a denominated observed sum and is never extrapolated.

Evidence publication uses four operational tiers:

- `blocked`: readiness and privacy-scanned diagnostics only;
- `mapping_only`: safe onboarding and readiness artefacts, without a scorecard;
- `partial`: bounded metrics with covered, eligible, and source-population denominators;
- `complete`: all requested signals and design-specific preconditions are satisfied.

These tiers are not statistical confidence levels and do not change the evaluation design's claim ceiling.

## Prepare an offline OpenTelemetry export

The toolkit does not connect to an observability backend or store credentials. Export OpenTelemetry LogRecords as an OTLP/JSON `ExportLogsServiceRequest`, then prepare the local file:

```bash
agent-eval-toolkit prepare-opentelemetry \
  --input path/to/logs.otlp.json \
  --mapping path/to/opentelemetry-mapping.json \
  --evaluation-manifest path/to/evaluation-manifest.json \
  --activity-log path/to/mapping-activity.jsonl \
  --output-dir path/to/prepared-evaluation
```

OpenTelemetry provides the interoperable timestamp, event-name, trace, span, resource, scope, and attribute envelope. The explicit mapping supplies workflow-run, business-status, configuration, quality, and economic semantics required by the evaluation. A trace ID is not treated as a workflow run unless that equivalence is approved.

LogRecord bodies and unmapped attributes are omitted from generated evidence. The converter emits canonical events, a workflow configuration, a raw-value-free source profile, mapping assessment, friction profile, issue register, redaction report, input fingerprints, and diagnostics. See `docs/OPENTELEMETRY_ONBOARDING.md` for the attribute contract and claim boundary.

## Input file expectations

### 1. Workflow config

The workflow config tells the toolkit how to interpret the raw logs for one pilot workflow family.

Sample file:

- `data/sample_inputs/pilot_workflow.json`

Important fields:

- `workflow_family`: logical workflow family name
- `workflow_definition_id`: versioned workflow definition identifier
- `source_schema`: which raw fields contain event id, timestamp, and event type
- `event_type_map`: mapping from raw event names to normalized event types
- `run_id_keys`: ordered list of raw fields to use as workflow run identity
- `trace_id_keys`: ordered list of raw fields to use as trace identity
- `step_name_keys`: ordered list of raw fields to use as workflow step name
- `status_field`, `attempt_field`, `actor_field`: raw fields used for metrics and reconstruction
- `cost_field`, `input_tokens_field`, `output_tokens_field`: observed cost signal fields
- `agent_configuration_id_field`, `agent_version_field`, `configuration_hash_field`: raw fields used for run-level configuration traceability
- `tool_name_field`, `tool_call_id_field`, `routing_decision_field`, `handoff_target_field`: optional fields for tool-call, routing, and handoff analysis
- `failure_mode_field`, `quality_score_field`: optional fields for reliability and quality reporting
- `capture_raw_fields`: allowlisted raw fields copied into evidence snapshots for auditability
- `allowed_metadata_fields`: canonical allowlist for raw fields copied into normalized event metadata
- `metadata_fields`: legacy/backward-compatible metadata allowlist; prefer `allowed_metadata_fields` for new evaluations
- `restricted_fields`: fields considered unsafe for unrestricted retention
- `redact_raw_fields`: fields that must be replaced with `[REDACTED]` when copied into evidence or metadata
- `evidence_mode`: evidence retention mode, defaulting to `anchor_hash_redacted_snapshot`

`anchor_hash_only` retains hashes and source anchors but clears both evidence snapshots and
normalized metadata. `anchor_hash_redacted_snapshot` retains only the explicit capture/metadata
allowlists, with every declared restricted field masked.

### 2. Raw log file

The raw log input must be JSONL:

- one JSON object per line
- each line is one telemetry event
- blank lines are ignored

Sample file:

- `data/sample_inputs/pilot_logs.jsonl`

### 3. Evaluation manifest

The evaluation manifest is required. It defines how the run should be interpreted as an evaluation, not just as raw telemetry processing.

Sample file:

- `data/sample_inputs/evaluation_manifest.json`

Important fields:

- `evaluation_id`: stable identifier for the evaluation package
- `evaluation_design`: one of `ab_test`, `before_after`, `monitoring`, `scenario_suite`, or `staged_rollout`
- `measurement_window`: start/end timestamps and timezone
- `baseline` and `comparator`: definitions used for comparison and interpretation
- `assumptions`: ROI/time-value assumptions, including optional sensitivity ranges
- `telemetry_requirements`: required and optional signals checked before scorecard generation
- `configuration`: agent configuration/version/hash evidence for traceability
- `interpretation_boundaries`: explicit limits on what the evaluation can support

The pipeline fails closed when required telemetry signals are missing.

### 4. Baseline context

This file is optional. It is only used for legacy assumption overrides. Prefer placing durable assumptions in the evaluation manifest.

Sample file:

- `data/sample_inputs/baseline_context.json`

Current fields:

- `manual_baseline_cycle_time_seconds`
- `manual_baseline_human_effort_seconds`
- `agent_human_effort_seconds` (only when active human effort is not observed per run)
- `loaded_labor_rate_usd_per_hour`
- `overhead_cost_usd_per_run`
- `tooling_cost_usd_per_run`
- `sensitivity`

These values do not affect observed metrics. They only override matching assumption-based sections of the scorecard and report. The deprecated `manual_baseline_duration_seconds` input is accepted for compatibility as elapsed cycle time only; it is never treated as human effort.

## Output files

### `input_validation.json`

Canonical source-shape validation, including missing or invalid signals and duplicate event identifiers. A failed preflight emits diagnostics but never a scorecard or evaluation report.

### `normalized_events.json`

Normalized telemetry events with:

- normalized event fields
- missing field flags
- evidence references back to the source file and line number
- allowlisted metadata only; unrestricted raw payload fields are not retained

### `workflow_runs.json`

Reconstructed workflow runs with:

- run id
- status and completion state
- duration
- retries
- interventions
- tool-call, handoff, routing, quality, and failure-mode summaries when present
- configuration identifiers and hashes when present
- observed cost and token totals when present
- missing telemetry flags
- event ids and trace ids
- evidence references

### `excluded_runs.json`

Runs reconstructed from telemetry but excluded from analysis because they are outside the manifest measurement window or missing timestamps.

### `telemetry_validation.json`

Minimum telemetry coverage result with:

- required and optional telemetry signals
- missing required schema signals
- missing required signals by workflow run
- required and optional coverage used by the tier classifier

### `scorecard.json`

Pilot scorecard with:

- evaluation design, baseline/comparator, configuration, and interpretation boundaries
- observed summary metrics
- assumption-based summary metrics
- sensitivity ranges when assumptions provide bounds
- comparator summary by agent configuration
- telemetry validation result
- missing telemetry summary
- per-run scorecards

### `redaction_report.json`

Data-protection report with:

- restricted fields
- redaction fields
- redacted field counts
- evidence mode
- pass/fail status for raw-retention policy

### `evaluation_package.json`

Audit index with:

- input fingerprints
- output artefact fingerprints
- toolkit, artefact-schema, Python, and dependency-lock provenance
- telemetry validation result
- redaction report
- taxonomy classification
- measurement-window summary
- warnings

### `pilot_report.md` and `enterprise_evaluation_report.md`

A Markdown report for pilot review with:

- evaluation design, baseline/comparator, and configuration evidence
- taxonomy classification
- measurement-window coverage
- telemetry coverage gate result
- observed summary
- comparator summary
- assumption-based summary
- missing telemetry summary
- per-run detail

Both files contain the same report content. `pilot_report.md` remains for compatibility and `enterprise_evaluation_report.md` is the clearer enterprise-case-study alias.

```bash
agent-eval-toolkit list-templates
```

Arguments:

- `--workflow-config`: required path to the pilot workflow config JSON
- `--raw-logs`: required path to the raw JSONL logs
- `--evaluation-manifest`: required path to the evaluation manifest JSON
- `--output-dir`: required directory for generated artefacts
- `--baseline-context`: optional path to legacy baseline assumption overrides JSON
- `--mapping-assessment`: optional mapping assessment required when the manifest declares it
- `--minimum-tier`: explicit CLI override for the manifest publication minimum
- `--overwrite`: explicitly replace known generated artefacts; without it, stale outputs are rejected

## Design choices

- The normalizer is config-driven but intentionally minimal.
- The framework is centered on workflow runs, not individual events as the primary reporting unit.
- Every normalized event carries allowlisted source evidence to support auditability.
- The evaluation manifest is the durable home for baselines, comparators, assumptions, telemetry requirements, and configuration evidence.
- Missing telemetry is surfaced on events, runs, and summaries.
- Undeclared telemetry capabilities are reported as unsupported (`null`), never as observed zero.
- Required telemetry gaps fail the pipeline before scorecard generation.
- Failed or incomplete runs are not eligible for positive time-saved or economic estimates.
- Productivity and ROI-style outputs are separated into assumption-based estimates.
- Real enterprise data should be staged into canonical JSONL outside this repository.
- Generated outputs retain anchors, hashes, and redacted snapshots, not unrestricted raw payloads.

## Troubleshooting

### `agent-eval-toolkit: command not found`

You likely have not activated the virtual environment.

Run:

```bash
source .venv/bin/activate
```

If the environment is active and the command is still missing, reinstall:

```bash
uv pip install .
```

### Import errors when running tests

Make sure the package is installed in the active environment:

```bash
source .venv/bin/activate
uv pip install .
python -m unittest discover -s tests
```

### You want to start over locally

Remove the old environment and recreate it:

```bash
rm -rf .venv
uv venv .venv
source .venv/bin/activate
uv pip install .
```
